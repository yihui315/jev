REVISION 2 (line-ending rule corrected)
------------------------------------------------------------------------
The re-derivation recipe below originally shipped `tr -d '\r'`. That was wrong
and weaver caught it: it deletes every CR, not only the line-ending one, so an
in-band CR injection is silently normalised to a clean-looking file. The recipe
now uses `sed 's/\r$//'`, and the measured numbers are unchanged because this
tree contains no lone CR anywhere -- meaning the original figures were right by
luck, not by construction. The numbers did not change; the method did.
See AEGIS_RENORM_CORRECTION.txt for the full evidence.

WHAT I GOT WRONG
------------------------------------------------------------------------
The sha256 values I reported to team-lead earlier were computed with a bare
sha256sum over the WORKTREE file. With core.autocrlf=true the worktree
carries CRLF while the committed blob carries LF, so a bare worktree hash is
NOT reproducible from a fresh checkout. Two further problems compounded it:
  * SECURITY_FINAL.json was committed twice (20c037f, then 46ff531), so the
    value I quoted described NEITHER final commit;
  * the value was computed BEFORE the self-reference commit, so it was stale
    on arrival.

Nothing about the security FINDINGS changes. Only the digests were wrong.

HOW TO RE-DERIVE (either is valid, say which you used)
------------------------------------------------------------------------
  committed artefact : git cat-file -p HEAD:<path> | sha256sum
  worktree as-is     : sha256sum <path>
  line-ending agnostic (either side may be CRLF or LF):
      ndiff() { git cat-file -p "HEAD:$1" | sed 's/\r$//' | sha256sum | cut -d' ' -f1; }
      nwork() { sed 's/\r$//' < "$1" | sha256sum | cut -d' ' -f1; }
      # ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^ ^
      # DO NOT replace the sed above with `tr -d '\r'`. That form is WRONG and
      # it fails silently. `tr -d '\r'` deletes EVERY CR, not just the one that
      # pairs with a LF, so an IN-BAND CR injection normalises to the same
      # bytes as a clean file. Measured on this host:
      #     clean   '...\n\nLoads the config\n'
      #     damaged '...\n\n\rLoads the config\n'   (a CR before 'L')
      #     tr -d '\r'      -> MATCH   (real damage hidden)
      #     sed 's/\r$//'   -> DIFFER  (correctly caught)
      #     non-zero-byte check -> not flagged either, so the two checks do
      #                           NOT substitute for normalisation here.
      # Only the line-ending CR may be removed; a lone CR is content.
      # Python: b.replace(b"\r\n", b"\n")   -- NOT b.replace(b"\r", b"")
      # See AEGIS_RENORM_CORRECTION.txt for the full write-up, and
      # tools/inc002_tree_check.py:120-126 for the reference implementation.
      # The MEASURED VALUES below were produced with the sed form. The earlier
      # issue of this file used tr -d; on this tree both agree (no lone CR
      # exists anywhere), so no number changes -- but the tr form was correct
      # by luck, not by construction.

NOTE ON THE LINE-DENDING RULE
--------------------------------------------------------------------------
Normalisation is CRLF -> LF only (`sed 's/\r$//'`, or
b.replace(b"\r\n", b"\n")). Never `tr -d '\r'`: it deletes EVERY CR, so an
in-band CR injection normalises to a clean-looking file and the check reports
MATCH on damaged content. Measured:
    clean   'ab\r\n'    -> tr: 61 62 0a
    damaged 'a\rb\r\n'  -> tr: 61 62 0a   MATCH  (damage hidden)
                            -> sed: 61 0d 62 0a  DIFFER  (caught)
