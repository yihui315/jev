AEGIS EVIDENCE SHA CORRECTION
========================================================================

Reason: CRLF normalisation. See INC002_CRLF_HASH_NOTE.txt (forge2).
Repo autocrlf setting: true

WHAT I GOT WRONG
------------------------------------------------------------------------
The sha256 values I reported to team-lead earlier were computed with a bare
sha256sum over the WORKTREE file. With core.autocrlf=true the worktree
carries CRLF while the committed blob carries LF, so a bare worktree hash is
NOT reproducible from a fresh checkout. Two further problems compounded it:
  * SECURITY_FINAL.json was committed twice (20c037f, then 46ff531), so the
    value I quoted described NEITHER final commit;
  * the value was computed BEFORE the self-reference commit, so it was stale
    on arrival.

Nothing about the security FINDINGS changes. Only the digests were wrong.

HOW TO RE-DERIVE (either is valid, say which you used)
------------------------------------------------------------------------
  committed artefact : git cat-file -p HEAD:<path> | sha256sum
  worktree as-is     : sha256sum <path>
  line-ending agnostic (either side may be CRLF or LF):
      ndiff() { git cat-file -p "HEAD:$1" | tr -d '\r' | sha256sum | cut -d' ' -f1; }
      nwork() { tr -d '\r' < "$1" | sha256sum | cut -d' ' -f1; }

NOTE ON THE FIRST ATTEMPT AT THIS FILE
------------------------------------------------------------------------
The first version of this note was produced by a PowerShell heredoc whose
reads came back empty, so it recorded the sha256 of the empty string
(e3b0c44298fc1c14...) for BOTH files. That is the same value a genuinely
zeroed file produces -- the broken script emitted exactly the artefact
INC-002 is about. It was caught by cross-checking against sha256sum, not by
reading the file. Rewritten here with every value read explicitly.
